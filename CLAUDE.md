# CLAUDE.md — Ours (private couples app)

Context for anyone (human or model) picking up this codebase.

## What this is

**Ours** is a private, just-for-two relationship app. One Expo codebase runs on iOS, Android, and web. Original brief in `Details.md`; it has since grown: a public landing page, a post-login home dashboard, a notification service, a calendar-based memory log, heart reactions, a shared bucket list, optional pairing, and (phase 2) a daily prompt with mutual reveal, time capsules, a date planner, per-partner wishlists with secret gift plans, and Sunday weekly reflections. **No stubs, no mock states.**

## Stack

| Layer | Tech |
|---|---|
| App | Expo SDK 53 + React Native 0.79 + Expo Router 5 (`react-native-web` for web) |
| API | ONE Vercel serverless function (`api/index.ts`) routing to modules in `api/_routes/` |
| Database | CockroachDB (Postgres wire protocol, `pg` driver) |
| Realtime | Ably (server publishes via REST, clients subscribe via scoped tokens) |
| Auth | Email+password, `node:crypto` scrypt, `jsonwebtoken` JWTs (30-day) |

## Commands

```sh
npm install
npm run migrate        # applies db/schema.sql (idempotent); RE-RUN after schema changes
npm run typecheck      # tsc --noEmit over app/ src/ api/ scripts/
npm run build:web      # expo export --platform web -> dist/
npx vercel dev         # API on :3000 (local)
npx expo start         # app; press w for web
```

Environment: `.env` from `.env.example` (`DATABASE_URL`, `ABLY_API_KEY`, `JWT_SECRET`, `EXPO_PUBLIC_API_URL` (stays EMPTY on Vercel), `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` for Web Push (generated once via `npx tsx scripts/generate-vapid.ts`), `MASTER_ENCRYPTION_KEY` for envelope encryption at rest (256-bit, base64; generated once via `npx tsx scripts/generate-master-key.ts`; if unset the app runs with encryption OFF so nothing breaks), `ADMIN_PASSWORD` gating `/admin/dashboard` (unset = dashboard locked), and `CRON_SECRET` gating the scheduled reminder endpoint `/api/cron/reminders` that the GitHub Actions in `.github/workflows/` call (unset = reminders return 503; the Actions also need repo secrets `CRON_SECRET` (same value) + `APP_URL`), and `AXIOM_TOKEN`/`AXIOM_DATASET` for searchable logs (unset = structured logs still go to stdout, see Observability), and `RESEND_API_KEY`/optional `RESEND_FROM`/optional `RESEND_TEST_RECIPIENT` for password-reset email (see the Auth bullet)). Deployed via GitHub import into Vercel; env vars live in Vercel project settings.

`npm test` runs vitest over `api/**/*.test.ts` AND `src/**/*.test.ts` (server route unit tests plus the app's PURE helpers, which must stay free of React/react-native imports to run under plain node; `memory-item.test.ts` guards the per-user hearts rule, `onboardingSteps.test.ts` guards the first-run step rules).

## Product structure

- **Landing** `app/(auth)/welcome.tsx`: public marketing page (hero, three feature cards, CTA). Signed-out users at `/` land here.
- **Auth** sign-up/sign-in. **Signup auto-creates a solo space** (couple row); pairing is optional. **Password reset (v22)** has two doors onto the same scrypt-hashed password: (1) signed-in **Change password** (Settings -> Account, a `Sheet` with current/new/confirm; `POST /api/auth/change-password` verifies the current password, then rotates in a fresh token so the change does not log you out); (2) signed-out **Forgot password** (`app/(auth)/forgot-password.tsx`, a 3-step email -> 6-digit code -> new password machine off the sign-in link). `forgot-password` emails a code via Resend (`api/_lib/email.ts`, fetch to Resend's REST API, no npm dep; `RESEND_API_KEY` + optional `RESEND_FROM`, defaults to the `onboarding@resend.dev` test sender), **always returns a generic success** (no account-existence leak), is rate-limited to 5 codes/email/hour, and invalidates prior unused codes so only the newest works. **`RESEND_TEST_RECIPIENT`** (optional): Resend's sandbox sender only DELIVERS to the email on your own Resend account too, not just sends-from restricted, so while testing this redirects every send there regardless of which account's email the app looked up (`toAddress()` in `email.ts`; the account lookup itself always uses the real submitted email, only the delivery address is overridden, and the email body names which account the code is actually for so testing multiple accounts stays unambiguous). Unset it once a domain is verified so real users get their own codes. `reset-password` verifies via the pure `api/_lib/password-reset.ts` (HMAC-keyed hash of the code, `resetCodeStatus` ok/missing/used/expired/mismatch, all collapsed into ONE generic error), sets the password, stamps `password_changed_at` (see security invariant 2), and returns `{token, user}` so they land signed in. The only password rule anywhere is signup's min 8 chars; no new strength rule was invented.
- **Pairing** `app/pair.tsx`: NOT a gate. Share your code or join theirs; joining migrates everything you authored into their space (see `api/_routes/couple-join.ts`).
- **Home** `app/(tabs)/index.tsx`: days-together count (basis: earliest anniversary milestone, else couple created_at; when there is NO anniversary yet the hero shows "Here is to you two ♥" + an inline "add the day it began" link instead of a misleading "0 days"), hero marks (both partners' avatars with a ♥ between; falls back to the initials monogram), a **milestone countdown banner** right after the hero when one's window is open (see the countdown bullet under Milestones; `data.countdown`, tap opens `/milestones`, fires the confetti shower once per open), invite banner when solo, "Your journey" points/level card, a **"Keeping each other on track" to-do card** (see the To-dos bullet; shows only when there is something to say, `weekTotal > 0 || overdue > 0`: "N of M done this week", an overdue line in `colors.danger` when anything is stuck, up to 3 named recent wins with who finished them, tap opens `/todos`), resurfaced memory (1 year ago today > 1 month ago today > random older), "Coming up soon" milestones (always rendered, with a "+ Add" header link; empty-state copy when none), latest pinned note, resurfaced memory, a **"Your weekly recaps" row** ("Looking back" section, `CalendarHeart` icon, links to `/reflections`) shown on every day except Sunday, when the `ReflectionCard` itself already occupies that spot (the saved recaps otherwise had no way back in once the Sunday card scrolled past). The bucket list is NO LONGER on Home (moved into the Wishes tab). Powered by ONE aggregate call: `GET /api/home` (still returns `bucket` for now, unused by the client; also returns `todos: {weekDone, weekTotal, overdue, todayTotal, todayDone, wins[]} | null`, catch-guarded for a pre-v19 deploy).
- **Wishes** `app/(tabs)/wishlist.tsx` (ONE tab, route `/wishlist`, label "Wishes"): the third redesign of this surface and the one the user chose from pitched options ("Wishing on stars"); the history in one line: separate screens -> merged with Ours/Mine/Theirs segments (hated) -> six tabs with a separate Bucket list tab (hated: "I don't want it to move to a separate tab") -> THIS. Two halves split like Memories splits calendar/timeline: side by side on web >= 900px, one scroll on narrow, nothing hidden behind segments. (1) **The night sky** ("Wished together", data = the old `bucket_items`, unchanged): an oxblood panel where every open shared wish is a gold ✦ (deterministic scatter by id hash, decorative `SKY_DUST` glyphs); serif "We wish..." composer + gold ✦ send; tapping a wish opens inline actions *It came true ♥* (marks done + fires `showHearts()`), *Plan it as a date* (navigates to `/dates` with `{ compose, wish: title }`, the propose sheet prefills), *Rewrite*, *Let it go* (two-step). **"Pull one down"** draws a RANDOM open wish into a Sheet ("This one fell for you") with plan-as-date / pull-another. Come-true wishes leave the sky for a parchment **"Came true"** list (gold ✦ + date, tap = back-to-sky/remove). (2) **Gift wishes**: Mine/Theirs mini pill toggle; tag-styled rows where the tag's "hole" doubles as the got-it tick on the partner's list; secret plans carry a small wax dot + "only you see this"; composer keeps the secret-vs-visible choice. **The experience|item category taxonomy is DEAD in the UI** (user: "why does it have to be experiences and things"); the columns remain, the server defaults them, clients never send or show them. FAB action is "Make a wish" (focuses the sky composer). Wishlist title/url/notes stay encrypted; bucket titles plaintext.
- **Timeline** `app/(tabs)/timeline.tsx`: the merge of what used to be two tabs, Memories and Notes, into one feed ("combine the note section and the memory section... call it the timeline"). Two parts. (1) Month calendar; days that hold a memory OR a note render a ♥ instead of the number. **Tapping a (non-future) day SELECTS it and lists that day's entries in a panel below the grid** (the cell fills oxblood to show which day is being read), rather than jumping into the composer as it used to: the calendar is a browser, and the space under it was otherwise dead. Selection starts on today so the panel is never empty; the panel's header carries "+ Add to this day", which is now the way to compose against a specific date (`memory_date` column). The panel INCLUDES pinned notes, unlike the feed, since the question it answers is "what is from this day" and a pinned note still belongs to its day. (2) ONE scrolling feed mixing photo cards and note cards, with day-of-week headers (e.g. "TODAY", "12 JUL 2026") separating groups. **Sort key is the day a thing is ABOUT, not when it was typed**: a memory sorts by `memory_date` (which the calendar lets you backdate), a note by the day it was written (`created_at`); this keeps the calendar and the feed in agreement, so a photo added today of a trip last summer drops into last summer where the calendar already says it belongs. Pinned notes are the one exception: they float above the whole feed in their own "Kept close" block, unsorted by day, because pinning means "keep this in front of me," not "file this by date." **ONE COMPOSER (`MomentComposer`)**: once the tabs merged, having separate "add a note" and "add a memory" acts stopped making sense, so there is now a single LinkedIn-style composer taking words, a photo, or both, and either half alone is a complete post. Tools left to right: photo (`ImagePlus`), ✦ Sparkles (deals another "spark" placeholder, never inserted text), Smile (emoji palette), Lock (seals a capsule), then the wax-seal ♥ send disc. The top of the feed is a slim **trigger row** (avatar + "Share a moment..." + a photo shortcut that opens the picker immediately), NOT a live input: the composer markup then exists exactly once and the feed keeps its vertical space, which is precisely how LinkedIn does it. Memory cards: photo, note, comment thread (MessageCircle always visible, expands INLINE Facebook-style via `MemoryComments variant="light"`) and hearts. Note cards: tiny deterministic tilt (`tiltFor(id)`, pinned cards sit straight on blush), one footer row (avatar + name + relative time, then Pin/Trash2/heart icons). Comments can be hearted (v16 `comment_hearts`, partner-only, server-enforced); note hearts are v9 (`PATCH /api/notes/:id { hearted }`, settles on the server response). On web >= 900px calendar and feed sit side by side. `MemoryImage` falls back to fetching the full photo for rows created before thumbnails existed (thumb_data null but has_photo true); do not remove that fallback. **`app/(tabs)/memories.tsx` and `notes.tsx` are now thin `<Redirect href="/timeline" />` stubs**, kept (not deleted) so a stale cached push notification or an old bookmark still lands somewhere real; every server-side deep-link table (`notification-routes.ts`, the client's `KIND_ROUTE` in `notifications.tsx`, `cron-reminders.ts`) points `memory`/`note`/`capsule`/`comment` kinds at `/timeline` now.
  - **Where a composed moment is STORED** (`src/lib/momentTarget.ts`, pure + unit-tested): one composer, but still two tables, because each keeps an ability the other lacks — `love_notes` rows can be PINNED, `memories` rows carry a backdatable `memory_date` and a comment thread. Rule: a photo goes to `memories`; **so does anything dated to a day that is not today**, even with no photo. That second clause is the subtle one and exists for a real trap: notes have no date column and sort by when they were written, so a wordless entry the user deliberately filed on a past calendar day would silently jump to today, contradicting the very cell they tapped. Plain words written today stay a note, so pinning keeps working. This asymmetry is deliberate but worth knowing: a text-only moment is pinnable and has no comments, a photo moment is commentable and not pinnable. `POST /api/memories` accordingly no longer requires `note` (it requires a photo OR words, and a captionless photo stores no ciphertext rather than the ciphertext of an empty string).
- **To-dos** `app/(tabs)/todos.tsx` + `api/_routes/todos.ts`/`todo-item.ts` (v19 `todos` table): a SHARED accountability list, the tab that took Notes' old slot once Notes merged into Timeline ("a person can add a to do list, and their partner will see it... both of them can be accountable"). One list per couple, not per person: either partner adds an item, either partner ticks it off or moves it to another day or reassigns it, and completing one notifies the other (`kind: 'todo'`). Only whoever ADDED an item may reword or delete it, enforced in `todo-item.ts` (a new PERMISSION split, not a delete exception like memories/dates: ticking/moving/reassigning is open to both, authorship still gates rewrite/delete). **Every to-do belongs to a day** (`due_date`, `assignee_id` NULL = "both of us" and is the default). **The screen is one day at a time with < > arrows** (chosen over a week-strip or one long scroll, "single day, arrows... when clicked on date calendar should pop up"); tapping the date label opens a `DayPickerSheet` month calendar to jump anywhere, past or future, since this is a planner, not a log (unlike the Memories calendar it does not disable future days). The same `DayPickerSheet` is reused for the per-item "Move this to..." action (Tomorrow / Pick a day), disambiguated by a single `pickerMode: 'jump' | 'move' | null` state rather than two booleans, specifically to avoid two Sheets ever being visible at once (an early draft had exactly that bug). **An unfinished item STAYS on its day and never rolls forward on its own**; the day view shows a small dot per calendar day (red = pending and overdue, gold = pending, olive = all done) and, on today's view, an "N unfinished from earlier · tap to catch up" banner that jumps straight to the earliest overdue day (`GET /api/todos` returns `earliestOverdue` for this). Reassigning cycles Both → You → Them → Both by tapping the assignee tag. Titles are encrypted at rest (`title_ct`, like notes); notifications are therefore always generic ("ticked something off your list"). **Realtime**: `todo.updated` carries `{ id, due_date, previous_due_date?, by, deleted? }`; `previous_due_date` (set only when the day actually changed) is what lets a partner watching TODAY's list live notice an item that just moved away, since the event's own `due_date` is the NEW day and would otherwise never mention the day it left. Feeds the path (`todos_done`, x2 points, catch-guarded for a pre-v19 deploy) and a Home card (see its bullet).
- **Avatars ("marks")** `src/components/Avatar.tsx`: curated set of lucide icons on tinted discs (ids must match `AVATAR_IDS` in `api/_routes/auth-profile.ts`); no upload, no emoji. Picked in Settings → Profile ("Your mark"), stored on `users.avatar` (v9), carried ONLY by `/api/auth/me` (self + partner) — list routes never join it because every author in a couple is one of the two `useAuth()` people. Fallback = serif initial disc. Shown on the Home hero, note cards, comment threads, and the Settings partner row.
- **Partner nicknames** (`users.partner_nickname` v11): a pet name you give your partner. Stored on the VIEWER's own row ("the name I call my partner"), so each partner sets their own independently. Resolved at `/api/auth/me`: `partner.display_name` becomes `nickname || realName`, so every screen reading `useAuth().partner` shows it with no other change; `partner.realName` + `partner.nickname` ride along for Settings and the notification-text swap. Set in Settings → Your space (calls `updateProfile({ partnerNickname })` then `refresh()`). The two server-generated name surfaces are handled explicitly: the notifications screen swaps `realName`→`nickname` in each stored line (`withNickname`), and `home.ts` resolves the pinned-note author. Plaintext by design (a term of endearment). Nullable/blank clears it. Catch-guarded selects (auth-me + home) keep a pre-v11 deploy from failing.
- **Onboarding** `app/onboarding.tsx` (route OUTSIDE the tabs group, v17): the guided first run, shown once to a NEW signup and never to an existing account. Gated by `users.needs_onboarding` (v17, `NOT NULL DEFAULT false` so every existing row is already "done" without a backfill UPDATE, which CockroachDB would reject in the same schema.sql; `auth-signup.ts` is the only place that sets it true, `PATCH /api/auth/profile { onboarded: true }` clears it). `/api/auth/me` carries `needsOnboarding` (catch-guarded); the tabs layout redirects on it. ONE route holding a step machine, not five routes. Steps: **add to home screen** (first, see its bullet for why) → **partner invite** (share a link / join theirs, reuses `joinSpace`) → **anniversary** → **your birthday** → **partner nickname** → **notifications**. Every step is skippable and leaves the field as empty as before; nothing is a gate (pairing especially). Which steps appear is decided by the pure, unit-tested rules in `src/lib/onboardingSteps.ts`: a step drops out when its data already exists (so closing the app mid-flow does not re-ask), the nickname step only exists once paired, and the notifications step only on a platform that can actually deliver. NOTE: there is no separate "your name" step, the signup form already collects it; the flow greets them with it instead. **Two first-run bugs found on device, do not regress**: (1) `signUp()` did not call `refresh()` the way `signIn()` does, so the space created during signup was absent from context and step 1 showed an EMPTY invite code until something else happened to hit `/auth/me`; (2) the notifications step never appeared on an iPhone because `canNotify` required `webPushSupported()`, which is false in a Safari tab (iOS exposes PushManager only to the installed app), so the step was filtered out instead of telling them to install. `canNotify` is now `webPushSupported() || webPushNeedsInstall()`, and the step renders an "Add Ours to your home screen" variant. `webPushNeedsInstall()` lives in `push-web.ts` and is shared with `NotificationsInvite`. (3) It STILL did not appear, because `ensureWebPushSubscribed()` in the tabs layout runs even on the render that redirects to onboarding (hooks cannot be conditional): on a device where permission was already granted it subscribed the brand new account within milliseconds, and the step then skipped itself as "already done". Two fixes: that effect is now gated on `!needsOnboarding` (onboarding owns the notification story for new signups), and **an existing subscription no longer removes the step at all** (`hasPushSubscription` is gone from `StepContext`); the step always shows on a capable platform and picks its own wording, including an "Notifications are on" confirmation variant.
- **Add to home screen** (`src/components/AddToHomeScreen.tsx` + `src/lib/install.ts`): the FIRST onboarding step, on **both platforms**, for a reason worth not forgetting. On iOS the home-screen app gets a **completely separate storage jar** from the browser (cookies, localStorage, even the service worker instance are not shared), so installing always costs one sign-in. Asking at the END of the flow made people redo a journey they had just finished; asking first costs only that sign-in, and everything else lives server-side (`needs_onboarding`, milestones, the couple) so the flow RESUMES. Do not move this step later. The screen is a DRAWN guide: a little phone built from views with the button you need circled in gold and an arrow pointing at it, because "tap share" is useless if you do not know where share lives. **Every iOS browser can install from the share sheet since iOS 16.4** (Safari, Chrome, Edge, Firefox, Orion, all WebKit, all giving the same push-capable home-screen app) so NOBODY is sent to Safari, an earlier version did that and it was wrong; the only per-browser difference is where the share button sits, which the arrow handles (Safari bottom toolbar, other iOS browsers top). On Chromium we capture `beforeinstallprompt` (`captureInstallPrompt()` runs early in the root layout, it fires once soon after load) and offer a REAL one-tap install. `shouldOfferInstall()` = any uninstalled phone; desktop never.
- **Session hand-off across the install boundary** (`src/lib/handoff.ts`): because of that separate storage jar, installing would otherwise dump someone on the sign-in screen seconds after signing up. Cache Storage is the one thing reported to be shared between the two iOS contexts, so `applySession()` stashes the token there and the installed app's first launch claims it (`claimSession()` in the auth bootstrap, before deciding they are signed out). Treated as a HAND-OFF, not storage: 15-minute expiry, deleted the moment it is read, cleared on sign-out. It is a documented trick rather than a supported API, so every call is wrapped and the fallback is simply the sign-in screen, where iOS Keychain autofills (both auth screens already carry the right `autoComplete` attributes, keep them).
- **Sharing the invite** (`src/lib/share.ts`): the code is the part people give up on, so the primary action on both the onboarding partner step and `app/pair.tsx` is **Send the invite**, which opens the phone's own share sheet (`navigator.share`, falling back to the clipboard) with a message plus `/sign-up?join=CODE`. The person who taps that link **never sees a code**: sign-up captures `join` and calls `joinSpace()` straight after the account exists (best effort, a stale code must not strand them). If they already have an account, the `(auth)` layout carries the code to `/pair?join=CODE` instead of bouncing them home and losing it. Reading the code aloud still works, demoted to a secondary affordance.
- **Milestones** yearly recurrence for anniversary/birthday, second-level countdowns. `milestones.person_id` (v17, nullable) says WHOSE a milestone is, which only birthdays need; anniversaries and every pre-v17 row leave it null and readers fall back to `author_id`, then the title text. `POST /api/milestones` accepts `personId` and validates it is a member of the couple; both the list and insert fall back through THREE column lists (v20 -> v17 -> legacy, see below) so a deploy before either migration keeps working.
- **Milestone countdown banner + daily reminder** (v20 `milestones.notify_days_before`/`.last_reminded_date`, `api/_lib/milestone-countdown.ts`, cron `kind=milestone`): every milestone (including ones added before this shipped, per the user's explicit "7 days by default" choice over an opt-in) gets a countdown window, editable per milestone in `app/(tabs)/milestones.tsx` (a Switch + a days-before field on each card, `PATCH /api/milestones/:id { notifyDaysBefore }`; 0 turns it off, 60 is the cap). While the window is open (`0 <= daysUntil <= notify_days_before`, pure and unit-tested in `milestone-countdown.ts` alongside `date-reminders.ts`/`streak.ts`), Home shows a celebration banner ("7 days to {label}" / "Today is {label}!") right below the hero, and the daily cron (`.github/workflows/milestone-reminder.yml`, 01:30 UTC) pushes both partners once a day, tracked by `last_reminded_date` so a retried run never double-sends. `{label}` resolves to the actual name of whoever's birthday it is via `person_id` (never a nickname or "your/their", since the banner is identical for both partners and a nickname is viewer-specific) for `kind: 'birthday'`, else falls back to the milestone's own title text; milestone titles are plaintext (not encrypted), so this is safe both in the banner and the push body. **The confetti request vs. the "no confetti" design rule**: the user explicitly asked for confetti; CLAUDE.md's own design system explicitly forbids it and mandates ONE sanctioned shower reused for every celebration. Flagged back to the user before building; resolved as "minimal confetti in the app's own palette, same mechanic as the hearts shower" — `showConfetti()` in `HeartsRain.tsx` is a second INVOCATION of the exact same shower engine (falling pieces, oxblood/gold/blush), not a second system: small rectangles instead of ♥ glyphs, nothing else changes. Fires once per Home open (`confettiShownRef`, same guard pattern as the nudge shower), from `home.ts`'s `countdown` field.
- **Daily prompt** (`api/_routes/prompts.ts`, home card + `app/(tabs)/prompts.tsx` history): one static-pool question per day, deterministic by date; answers are private until BOTH partners submit, then reveal. One submission per person per day.
- **Streak** (streak math in `api/_lib/streak.ts`, wired in `prompts.ts`): a day counts when BOTH partners answered that day's prompt. **Computed from the source of truth** (`computeStreak(mutualDays, todayUTC)`): the whole streak is re-derived every read from the set of days both partners answered, so it can never drift (the old incremental counter double-fired / mis-timezoned and showed wrong numbers). Pure + unit-tested (`api/_lib/streak.test.ts`, 14 cases incl. "2 days reads as 2" and the grace-visibility set). UTC days, one grace day per Monday-to-Sunday UTC week; `computeStreak` also returns `graceAvailable` + `graceDay` so the UI can say plainly whether the week's one free miss is still in hand. `couples.current_streak_days/longest_streak_days/last_streak_date` are now just a cache for admin analytics, refreshed on each reveal by `advanceStreak`; `grace_used_week` is unused. `streakStateFor` = read view. Surfaced from day one: hero chip on Home, prompt-card lines, and the prompts screen header carries a persistent "how the streak works" explainer (user could not tell what it counted). **The full streak screen** `app/streak.tsx` (outside the tabs group, opened by the Home chip and a "See your streak" link on the prompts screen): the count + what it means today, a **grace day card** (unused / used, naming the day it covered; free and automatic, and deliberately NOT a purchasable freeze since Ours has no billing), both partners side by side with today's state, and a **shared month calendar** mirroring the Memories one (♥ = both answered and the day counts, ♡ = only one of you, today outlined). Fed by `GET /api/prompt/today?days=1`, which adds a `days: [{date, mine, theirs}]` array (one year, one grouped query, no answer text read); the flag keeps the plain prompt card a light request. **Streak celebration**: when a day becomes mutual (both answered), the sanctioned hearts shower fires once per prompt day as positive reinforcement (Home `celebrateStreak`, guarded by `celebratedDateRef`; fires from the answer-submit response for the second answerer and from the `prompt.revealed` event for the first). No leaderboards.

Reaching a new place = the sealed "Somewhere new" ceremony with `madeOfSummary` ("A place made of 18 memories, 12 answered questions and 9 notes", counts of real things, never points); last celebrated level still in `localStorage['ours.story-chapter']`. LEVELS is duplicated client-side; keep both in sync. LEVELS + POINT_SOURCES are duplicated client-side in `app/(tabs)/index.tsx`; keep both in sync with home.ts.

New deps: `expo-audio` (recording + playback, the SDK 53-era replacement for `expo-av`'s recorder), `expo-file-system` (reads a native recording's `file://` URI into base64 for upload; web instead re-fetches its own `blob:` URI and lets `FileReader.readAsDataURL` produce the base64 directly), and `ffmpeg-static` (server-side only, the cross-platform-playback fix, see below). `src/lib/audioWaveform.ts` (pure, unit-tested) holds the math: `meteringToLevel(db)` maps expo-audio's dBFS metering onto a 0..1 level with a -50dB floor, `downsampleWaveform(samples, 40)` buckets an arbitrary-length run of real sampled levels into the fixed `WAVEFORM_BARS` stored with the message (pads with 0, never fabricates a shape for a clip with no readable levels), `formatClipDuration(ms)` gives the shared mm:ss both the recording timer and a played bubble use. `src/lib/useVoiceRecorder.ts` is the recording hook: expo-audio (a custom `RecordingOptions` built off `RecordingPresets.HIGH_QUALITY` with mono/64kbps, tuned for speech, not music) drives the actual capture and encoding identically on every platform, one code path for the risky part; live level sampling is the one thing that has to fork, because **expo-audio implements metering on iOS and Android only, never on web** (confirmed by reading its own web source, `AudioModule.web.ts`; `RecorderState.metering` is simply never set there). Native polls the recorder's own `useAudioRecorderState(...).metering`; web runs a small `AnalyserNode` alongside the recorder purely to sample levels (a second concurrent `getUserMedia` stream, which browsers allow once permission is granted) and is fully best-effort: any failure there just leaves the waveform flatter, it never blocks or breaks the actual recording. Duration is measured with a plain `Date.now()` timer in the hook rather than trusted from expo-audio's own status, because its web recorder resets `currentTime` to 0 inside its own `'stop'` event listener, which can race the very `stop()` call that would read it. **Recording format vs. playback format, and why they are two different problems**: at the RECORDING step, `pickWebMime()` (`src/lib/useVoiceRecorder.ts`) asks `MediaRecorder.isTypeSupported()` and picks whatever the current browser can actually ENCODE (`audio/mp4` on Safari, `audio/webm` on Chrome/Firefox, since Safari's MediaRecorder throws at construction time if asked for a webm mimeType it does not support) — this is purely about making recording succeed on every browser, not about playback. **Playback compatibility is a separate, server-side guarantee.** Every clip, in whatever format it was recorded (native `.m4a`, Safari's `audio/mp4`, Chrome/Firefox's `audio/webm`), is normalized by `transcodeToAac()` (`api/_lib/transcode.ts`) into ONE canonical AAC-in-`.m4a` file (`audio/mp4`) BEFORE it is ever stored, using a real `ffmpeg` binary (`ffmpeg-static`, a normal npm dependency bundling a static binary per platform, spawned via `child_process.execFile`; writes to a `mkdtemp` scratch dir under the OS temp dir, cleaned up in a `finally`). This runs unconditionally, even on an already-mp4 native recording, deliberately: one code path, no "skip if already compatible" branch that could itself drift out of sync with what actually counts as compatible. **This is what closes the gap a documented limitation would otherwise have left**: without it, a clip recorded on Android/desktop Chrome (webm) could silently fail to play back in an iOS Safari `<audio>` element, which has unreliable WebM demux support; with it, every stored clip is the one format every platform's native player (AVPlayer, ExoPlayer) and every modern browser can decode, the same guarantee a mainstream chat app gives (their apps bundle their own cross-platform audio decoder instead; this app leans on ffmpeg once, server-side, at write time, which is the dependency-appropriate equivalent given the existing stack). Fails LOUD on a transcode error (500, "Could not process that voice note. Try again.", logged as `chat.voice_transcode_failed`) rather than falling back to storing the untranscoded clip, which would silently reintroduce the exact bug this closes. **Vercel bundling**: `ffmpeg-static` resolves its binary path dynamically (`path.join(__dirname, ...)` built from a value read out of its own `package.json` at runtime), which Vercel's automatic dependency tracer cannot always follow; `vercel.json` force-includes it via `functions["api/index.ts"].includeFiles: "node_modules/ffmpeg-static/**"`. - **Secret chat** (`app/chat.tsx`'s secret mode, `api/_routes/secret-chat.ts` + `secret-code.ts`, `api/_lib/secret-chat.ts`/`secret-session.ts`, `src/lib/secretChat.ts`, v26): a SECOND thread inside the same couple, behind a 4-digit code, whose messages disappear on a per-message timer. Reached from a **"Secret" toggle in the chat header's right corner** (the spot the user circled in a screenshot). Chosen over a hidden gesture via `AskUserQuestion`: a snoop can see a secret thread exists but cannot open it, the same trade WhatsApp's locked chats make; plausible deniability was offered and declined.
  - **EXPIRY IS CRYPTO-SHREDDING, NOT DELETION. This is the whole design and the reason the feature is honest.** "DELETE the row" erases nothing in CockroachDB: it writes a tombstone, the previous MVCC version stays readable via `AS OF SYSTEM TIME` until GC runs (hours, and not a setting we control on Cockroach Cloud), managed backups keep a copy for weeks, and the row lives on three replicas. So every secret message is sealed under **its own random 256-bit key** (a third envelope layer: master key -> couple DEK -> per-message key -> the fields), the wrapped key is a ~60 byte row in `secret_message_keys`, and expiry destroys the KEY. The ciphertext is then noise for everybody, permanently. Three things this buys over deleting the message row: shredding a 12MB photo message costs one tiny delete; **it fails SAFE against our own future bugs** (a later query that forgets `AND (expires_at IS NULL OR expires_at > now())` returns unreadable bytes instead of leaking a message, which is a far likelier failure than a breach); and keys are always destroyed BEFORE the rows they open, so a half-finished sweep leaves messages dead rather than alive. **What it does NOT buy, stated plainly**: while a message is alive the server can read it, so the operator can. Only real end-to-end encryption closes that, and a 4-digit code cannot be its key (10,000 combinations, brute-forced offline in milliseconds). `envelope.ts` remains the documented swap point if that is ever wanted.
  - **The code is a LOCK ON THE DOOR, not the key to the safe.** Two mechanisms for two different threats: the code stops someone holding your unlocked phone, the shredding stops the database remembering. scrypt-hashed via the same `hashPassword`/`verifyPassword` the account password uses, stored **per USER** (`users.secret_code_hash`) so each partner unlocks their own device independently. Escalating lockout (`lockoutMinutesFor`: nothing for 4 tries, then 1/2/4/8… minutes per further batch of 5, capped at 60). Set/reset in Settings -> Privacy, **always requiring the account password, even the first time**: without that, someone holding an unlocked phone could set a code and lock the real owner out of their own thread. **Reset only, never reveal** (the user offered "show them the code after their password" as an alternative; showing it needs reversible storage, which is both weaker AND more work than one reset form, so it was declined with reasons). A wrong code always points at Settings rather than dead-ending.
  - **Unlocking buys a real credential, not a client boolean**: `POST /api/secret-code/unlock` returns a 15-minute JWT carrying `{secret: true}` + the user id (`secret-session.ts`, shaped like `admin.ts` so it can never be confused with a session token, and bound to a user so one partner's grant is not the other's). It rides `X-Secret-Token`, is held **in memory only** on the client (never localStorage, unlike every other token here) so a reload re-locks, and its expiry IS the auto-relock, with no timer to schedule.
  - **The timer starts when the message is READ, not when it is sent** (v27 `messages.timer_started_at`). The v26 build stamped `expires_at` at send, which meant a 1-minute message sent while your person was asleep was gone before they ever saw it; the countdown is meant to limit how long something LINGERS, not to race the recipient. `POST /secret-chat/seen` is therefore what starts the clocks, in one UPDATE guarded four ways: `sender_id != me` (your own reading never starts your own message), `timer_started_at IS NULL` (only once, so a second read cannot push a deadline out), `kept_by IS NULL`, and `ttl_seconds > 0`. The new deadlines ride the `secret.chat.seen` event so the sender's open thread switches from waiting to counting down live, with no refetch. Verified against the real database: the reader's arrival started only the partner's message, left their own waiting, and a repeat read changed nothing.
  - **Four states from three columns**, no extra flag: `ttl_seconds` null/0 = timer off; `ttl_seconds > 0` + no start + not kept = **waiting to be read** (no countdown shown); + kept = paused; `expires_at` set = counting down. `isAwaitingRead` is the pure predicate.
  - **Per-message timers, stamped at send** (`ttl_seconds`): changing the couple's timer affects messages sent after the change and nothing else, and changing it back restores the old window for the next ones. Existing messages always keep the deal they were sent under (WhatsApp's rule, and exactly what was specified). Options 1 min / 1 hour / 24 hours (default) / 7 days / off; **the list is served by the API so there is one source of truth**, not a client copy kept in sync by hand. A change is never silent: it writes a contentless `system_text` notice into the thread naming who changed it, which renders as a centred chip and needs no key.
  - **Keep** pauses one message's timer (`expires_at = NULL`, `kept_by`); **un-keeping restores the ORIGINAL deadline** (`unkeepExpiry` = `timer_started_at` + the ttl it was sent under), which is usually already past, so it goes at once. Deliberately not "now + the current timer", which would let keep-then-unkeep EXTEND a message's life, the opposite of what the button means; and a message kept before it was ever read returns to WAITING rather than getting a fresh window. Turning the timer off is the chat-level equivalent.

A bare count reveals only "something arrived", which the visible-but-locked toggle already announces. - **Scheduled reminders** (`api/_routes/cron-reminders.ts`, `.github/workflows/`): a PWA cannot schedule its own notifications, so scheduled GitHub Actions ping `POST /api/cron/reminders?kind=...` (gated by `CRON_SECRET`, Bearer; unset = 503). `kind=daily` (once/day, `daily-reminder.yml`, cron 13:30 UTC = 7:00 PM IST): for every couple that added NO memory and NO note that UTC day, both partners get a "keep one small thing" Web Push. `kind=dates` (hourly, `date-reminders.yml` — NOTE: the user deleted that workflow file in commit 20d0e1d, so date reminders do not currently run): for each accepted, not-yet-logged, dated proposal, both partners get a **generic** (title is encrypted) push at ~24h/6h/1h before, one per threshold, tracked by `reminded_24/6/1` flags (pure decision logic in `api/_lib/date-reminders.ts`, unit-tested). `kind=prompt` (once/day in the morning, `prompt-reminder.yml`, cron 01:30 UTC = 7:00 AM IST): everyone who has not answered today's prompt yet gets a "a fresh question is waiting" push to `/prompts`. `kind=game` (TWICE a day, `game-reminder.yml`, cron 07:30 UTC = 1:00 PM IST and 13:30 UTC = 7:00 PM IST): anyone whose couple has a This-or-That round open that THEY have not played gets a nudge. Who is actually waiting is decided by `hasUnplayedRound` in `api/_lib/game-rounds.ts` (pure, shared with the game route), so a run landing between rounds reports `nothing-open` and sends nothing rather than nagging; it deliberately does NOT fire when you are merely waiting on your partner (a push to you cannot fix that) and skips solo spaces entirely (a mutual-reveal game is pointless alone). One query for the day's answers, grouped in JS, never one per couple. `kind=milestone` (once/day, `milestone-reminder.yml`, cron 01:30 UTC = 7:00 AM IST): for every milestone whose countdown window is open (v20 `notify_days_before`, see the Milestones countdown bullet), both partners get "N days to {label}" / "Today is {label}!", tracked by `last_reminded_date` so a re-run never double-sends the same day. This same kind ALSO fires two **couple-level** reminders (v22, pure math in `api/_lib/couple-milestones.ts`, unit-tested): the **monthly anniversary** ("N months together today", off the earliest `kind='anniversary'` milestone, on the day-of-month matching it — clamped to the last day for short months, and skipping the month that coincides with the yearly anniversary so it does not double the countdown; couples with no anniversary are skipped) and the **50-day app tenure** ("50 days with Ours", off `couples.created_at`, at every 50-day multiple, sending only the HIGHEST threshold reached if a run was missed). One grouped query, deduped by `couples.last_monthly_anniversary_sent` / `.last_fifty_day_notified`. Unlike the countdown push, these two DO write a bell row (via `notifyCouple` in `notify.ts`, which inserts under a `SYSTEM_ACTOR` all-zero sentinel so BOTH partners see it in the pane AND get the push, reusing `kind:'milestone'`); the confetti/Home banner for them is a deliberate follow-up, not built this pass. The countdown reminders still write no notification rows (self-reminders must not crowd the bell). Every kind returns a full skip/fail report the workflow prints (see Observability). Setup needs `CRON_SECRET` in Vercel + repo secrets `CRON_SECRET` (same) & `APP_URL`; the workflows are UTC, so tune the cron times.

### Envelope encryption at rest (`api/_lib/envelope.ts`)

The single encrypt/decrypt boundary (a future move to E2E is a swap of this module + a client layer, not a route rewrite). Two key layers: a **master key** (256-bit, base64 in `MASTER_ENCRYPTION_KEY`, never in the DB) wraps a per-couple **DEK** (256-bit random, stored AES-256-GCM-wrapped on `couples.wrapped_dek`); field values are encrypted with the couple's DEK. Ciphertext layout per value: `iv(12) || ciphertext || authTag(16)` as one `BYTEA`.

- API: `encryptionEnabled()`, `freshWrappedDek()` (used by `invite.createCoupleForUser`), `encryptField(coupleId, plaintext) -> Buffer|null`, `decryptField(coupleId, blob) -> string|null`, `readField(coupleId, ct, plaintext)` (prefer decrypted ct, else the plaintext column).
- **Graceful degradation**: with no master key set, every helper returns null and callers read/write plaintext exactly as before, so the deployed app keeps working until the key is provisioned. Legacy couples get a DEK minted lazily on first use.
- **Storage pattern**: each encrypted column has a `<field>_ct BYTEA` beside the original. When encryption is ON, writes store the plaintext column empty (`''`/NULL) and the ciphertext in `_ct`; reads use `readField` (decrypt `_ct`, fall back to plaintext for old/never-backfilled rows). Old plaintext columns are NOT dropped (additive only). `scripts/backfill-encryption.ts` encrypts pre-existing rows (idempotent; blanks plaintext after).
- **Encrypted fields**: `memories.note`, `love_notes.body` (covers note/memory time-capsule content), `daily_prompt_answers.text`, `wishlist_items.title/url/notes`, `date_proposals.title/location`, `messages.body` (chat), `todos.title`. NOT encrypted (by design): milestone titles (list-view), bucket titles, reflection counts, timestamps, FKs, wishlist `secret` flag. `notify()` text must never embed an encrypted value (it would leak into the plaintext `notifications` table) — wishlist/date/todo notifications are deliberately generic.
- **Pairing migration**: `couple-join.ts` re-wraps the migrated encrypted fields (`memories.note_ct`, `love_notes.body_ct`) from the joining user's DEK to the target couple's DEK inside the merge transaction (`recryptBlob`), so content stays readable under the new key. Any encrypted field that becomes migratable later must be added to that route's `MIGRATED_CT` list.
- **Ably** carries plaintext for these fields (server already holds it; the channel is TLS + subscribe-only scoped tokens). "Encryption at rest" is about the database, not the realtime hop.
- **`/api/auth/me`** returns `encryption: boolean` plus `encryptionCode` (the "seal code": `keyFingerprint()` = SHA-256 of the couple's DEK with a fixed context string, mapped to 8 chars of the invite alphabet as `XXXX-XXXX`; one-way, identical for both partners, shown in Settings → Privacy so the couple can compare phones). The client threads both through `useAuth()`; `LockBadge` on composers and the Privacy copy never overclaim when the key is absent.
- **Key rotation (not automated)**: to rotate `MASTER_ENCRYPTION_KEY`, for every couple: unwrap `wrapped_dek` with the OLD master key, re-wrap with the NEW one, write it back (one pass, DEKs and field ciphertext are untouched). Rotating a couple's DEK instead means decrypting every field with the old DEK and re-encrypting with the new one. Never change the master key without re-wrapping, or all data becomes unreadable.

## Security invariants (do not weaken)

1. Every couple-scoped query filters by the authenticated user's `couple_id`; privacy lives in the API.
2. JWT carries only `sub`; `requireUser` re-reads the user row per request so couple_id is never stale. Tokens are stateless 30-day JWTs with one kill switch: `users.password_changed_at` (v22). A password change (Settings) or a reset stamps it, and `requireUser` rejects any token whose `iat` (whole seconds) predates that stamp, so a reset actually invalidates a stolen token. The stamp is NULLABLE with no default (a NULL never revokes), so the deploy logs nobody out; the acting device is handed a FRESH token so it survives its own change.
3. Ably tokens are subscribe-only, scoped to the user's own couple channel (`/api/ably-token`); the API key never leaves the server.
4. Spaces cap at 2 members; joining a full space is rejected. Deletes are own-content-only EXCEPT (a) memories, which either partner may delete, and (b) ACCEPTED date proposals, which either partner may edit or call off since both agreed to them (an open proposal stays its proposer's). couple_id is still enforced in every case; both exceptions are intentional and confirmed by the user.
5. To-dos split the permission differently from a delete exception: DONE/DUE_DATE/ASSIGNEE are shared (either partner may tick something off, move it, or reassign it, per `todo-item.ts`), but TITLE edits and DELETE stay author-only, same as everything else. Do not read this as a precedent for weakening delete ownership elsewhere; it is a separate axis (use vs. authorship) specific to a shared checklist.

## Observability (`api/_lib/log.ts`, `src/lib/log.ts`, `POST /api/logs`)

One structured-JSON pipeline, server and client. Every line is `{ _time, level, event, service, env, ...fields }`.

- **Sinks**: always stdout (Vercel function logs); additionally **Axiom** when `AXIOM_TOKEN` + `AXIOM_DATASET` are set (`AXIOM_URL` only for the EU region). Unset = stdout only, nothing breaks.
- **Server**: `log(level, event, fields)` buffers per invocation; `route()` flushes ONCE **after** the response is written, so shipping logs never sits in the user's latency path. `flushLogs()` never throws and gives up after 2.5s. **It hands the in-flight ingest to Vercel's `waitUntil` when the platform offers one** (read off the `@vercel/request-context` global rather than adding the `@vercel/functions` dependency for one call; absent it, the caller's await is the fallback, which is the old behavior). This is not optional polish: Vercel treats a finished response as a finished invocation and can FREEZE the container mid-fetch even while we await, suspending the request until a later invocation thaws it, at which point the overdue abort timer fires and the batch is lost. The tell was `axiom ingest error: This operation was aborted` printed at the head of an unrelated later request. Do not go back to a bare await.
- **Automatic coverage**: `route()` emits `http.request` (method, path, status, duration_ms, requestId, plus the error message on a 4xx/5xx) for every endpoint, so a new route is instrumented the moment it exists; `requireUser` stamps `user_id`/`couple_id` onto the request's log context (`logContext(req, {...})` adds more). `api/index.ts` logs `http.no_route`. `db.ts` logs `db.query_failed` + `db.slow_query` (>1s).
- **Push has the deepest instrumentation** because it is the least observable feature: `push.send` on EVERY attempt with a machine-readable `reason` from `PushReason` (`notifications-off` | `no-subscription` | `vapid-not-configured` | `invalid-subscription-json` | `subscription-expired` | `send-failed` | `native-not-provisioned`), plus `endpoint_host`, the push service's own `push_status`/`push_body`, and a `source` tag naming the caller (`notify:<kind>`, `cron:daily`, `cron:dates`, `chat`, `test`). Also `push.vapid_missing`, `push.subscription_stored`, `notify.sent`.
- **Cron reminders**: `POST /api/cron/reminders` returns a full report (`users`, `eligible`, `sent`, `skipped{reason:n}`, `failed{reason:n}`, `missing_vapid_env`) and logs it as `cron.summary`; `cron.date_checked` carries each date's `hours_until`. The GitHub workflow PRINTS the body, fails the job on a non-2xx, and warns on `"sent":0`, so a green run that delivered nothing says why in the job log. `cron.unauthorized` catches the classic repo-secret-vs-Vercel-env drift.
